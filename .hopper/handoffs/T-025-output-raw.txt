   102	  步骤 0：aggregate 计费前置校验（仅 billingAttribution:'user_tenant_aggregate' 部署适用）
   103	         → 若 deploymentTokenRef 缺失，同步拒绝 aggregate_billing_requires_deployment_token，
   104	           不进入下方步骤，Creating 直接失败，见 §2.3
   105	  步骤 1：预分配 sessionId（adapter 本地生成 UUID；此时原生内核会话尚不存在）
   106	  步骤 2：铸造计费 token（newapi POST /api/token/，写入 SessionHandle.billing.tokenRef）

   108	Creating → Active(idle) → 紧接着首条 send() 发出（进入 §3 生命周期状态机 + D5.1 Turn 状态机）
   109	  │
   110	  ├─ send() 成功（res.send() 返回 {runId}）——正常进入 RUNNING，见 D5.1 §2
   111	  │
   112	  └─ 首条 send() 本身失败（**v2.2 收残：T-024 F-01，补失败分支**——createSession 已经
   113	      resolve、`SessionHandle`/`sessionId` 已真实存在，内核侧原生会话已建立，这与下方
   114	      "步骤 0-3 任一步失败"的 Creating 失败分支是两个不同的失败点，不得混同）：
   115	      唯一终态是 **Active(idle) + 首发失败标记**——**不回退 Draft**（session 已存在，

   120	      approvalProfile/toolset）已随 createSession 完成而冻结，**不因 send 失败重新
   121	      开放编辑**——若想更换配置，仍需按 §2.2 既有规则新建一个 Draft Chat，不得为这
   122	      一失败分支单独开一个"回到可编辑"的例外
   123	Creating → [创建失败]      （步骤 0-3 任一步失败，见 §2.3；D1 §2.1 明确"步骤 1-3 之间任一步失败
   124	                            的处理规则不承诺跨步骤原子性"——但因为触发时点已经后移到"用户确认要
   125	                            发送"这一刻，创建失败时 Chat 退回 Draft 态即可：composer 保留用户已
   126	                            输入的首条消息内容与已选配置，用户可修改配置后重试，不遗留半成品
   127	                            sessionId 列表项）
   128	```

   150	**内部执行序列（v3.2 修订：步骤重排+步骤 1 新增，消解 codex T-010 BLOCKER-2 残留"createSession 无预分配 id"时序缺口；v3.3 新增步骤 0 前置校验，消解 codex T-011 M5）**：
   151	
   152	0. **aggregate 计费前置校验（v3.3 新增）**：若该内核部署实例的 `billingAttribution`（部署时静态声明，见 §4.1）为 `'user_tenant_aggregate'`，且 `config.newapiEndpoint.deploymentTokenRef` 未提供，`createSession` **同步拒绝**（`aggregate_billing_requires_deployment_token`，见 §9.1），不进入下方步骤 1-3——aggregate 模式下 `deploymentTokenRef` 是 §7 唯一的计费查询主体，缺失它却仍创建 session，等于承诺了一个将来注定查不到账的 `SessionBillingSnapshot`。`billingAttribution:'session'` 的部署不受本步骤约束（本字段本就不参与该模式下的查询，见上方 §2.1 字段说明）。
   153	1. **预分配 `sessionId`**（v3.2 新增，原步骤 1"resume 校验"下移为步骤 1a）：adapter 本地生成一个 UUID 作为该 session 的 `sessionId`，此时原生内核会话**尚不存在**。若 `config.resume` 提供，则复用该已存在 session 的 `sessionId`（本步骤退化为查找而非新铸）。
   154	   - 1a. resume 校验（同 v3.1，未变，位置下移但内容不变）：`config.resume` 提供时校验目标 session 是否可 resume，不可 resume（如 openclaw resume-after-delete 场景，见 §12 第 4 条）则显式 reject，不静默新建。
   155	2. **铸造计费 token**：调用 newapi `POST /api/token/` 为该 session 铸造一个专用 token（`name=session-<sessionId>`，此时 `sessionId` 已在步骤 1 铸造完毕，不存在"无预分配 id 却已引用它"的时序缺口），写入返回值 `SessionHandle.billing.tokenRef`（§7）。本步骤只完成"铸造+记录引用"，**不等于**归因已经成立——`tokenRef` 对应的 key 是否被实际配置进该 session 的模型调用出口（§7 注入链契约步骤④）是另一个独立的、由 §4.1 `billingAttribution` 权威声明的问题。
   156	3. 向目标内核发起原生会话创建；成功后取得内核返回的原生会话 id，写入 `SessionHandle.kernelSessionId`（v3.2 新增字段，见上）。

    69	### 3.2 菜单项渲染规则（D5 设计决策，遵循 foundation 原则 5 的扩展点纪律）
    70	
    71	菜单可见的 sandbox 档位 = `capabilities().sandboxLevels`（若声明）∩ 本地 Settings 已 enable 集合 ∩ 组织策略允许集合。**不得硬编码三个 if 分支**——`sandboxLevels` 是可选数组字段，未来任何新增档位（如 Computer Use 专属隔离环境，见 §10）都应该是"数组多一个值，UI 自动多渲染一项"，不是"UI 代码需要跟着改"。

   125	**核心设计约束（本页反复强调，避免后续实现阶段遗忘）**：无论 D5.7 的 UI 上呈现多少层级的选择（推荐档/Advanced/effort/speed），**最终传给 `createSession` 的只有一个 `config.model: string` 字段**——D1/D2 没有第二个参数可以携带 effort、speed、供应商等维度。因此：
   126	
   127	- **D5 设计决策**：D5 的 Server/newapi 路由层需要自行定义一套"UI 选择组合 → `model` 字符串"的编码约定（例如把档位+effort+供应商编码进一个复合标识符，或反过来用一个不透明的路由 key 代表整个组合），这套编码约定完全是应用层产物，D1/D2 对其内部格式没有任何规定，也不校验其合法性——`model?: string` 对 D1 而言就是一个透传的不透明字符串。
   128	- 这也意味着：如果用户在 Advanced 里选择了"某个模型 + High effort"，实际生效与否、是否被 newapi 正确解析，D1/D2 这一层**完全无法验证**——`createSession` 只会在 RPC 层面成功或失败（`RejectionFailure`），不会告诉调用方"你传的这个 model 字符串对应的 effort 是否被下游正确识别"。这一诚实边界应体现在 UI 上：Advanced 面板提交后，唯一能确认的是"会话已创建"，而非"effort 档位已生效"——后者依赖应用层自己的路由实现是否正确，协议层不提供这层保证。

   130	### 3.4 状态机：模型/effort 选择控件（区分"新建 Chat"与"已有 Chat 内切换"两条轨道）
   131	
   132	这是本页状态机设计的核心，也是与 [[d5-00-foundation]] §3.2 Goal/Subagent 诚实缺口同类型的一处关键分歧点。
   133	
   134	**v2 修复：与 [[d5-2-sessions]] §2.2 统一术语（消解 T-023 F-01）**——下方"轨道 A"里的 `Recommended`/`AdvancedExpanded`/`PendingCreate` 三态，对应的正是 [[d5-2-sessions]] §2.2 定义的**草稿态（Draft Chat）**内部的 composer 子状态（`PendingCreate` = Draft 态下 composer 已配置完毕、等待发送）；`CommittedToSession` 对应 [[d5-2-sessions]] §2.2"首次发送触发原子 `createSession()`+`send()`，config 冻结"这一跨全部子面统一的权威时点。本页 v1 版本独立推导出这一状态机时尚未与 D5.2 显式对齐术语（当时 D5.2 v1 错误地把 createSession 时点放在"点新建"那一刻），v2 修复后两页共享同一条时点权威，不再是各自平行的结论。
   135	
   136	**轨道 A——Draft Chat 内选择模型/effort，首次发送时冻结（D1/D2 有直接对应，confirmed）**：
   137	
   138	```
   139	Recommended（默认态，展示推荐档滑块；Chat 处于 Draft，无 sessionId）
   140	   │ 用户点击 Advanced
   141	   ▼
   142	AdvancedExpanded（展示具体模型/effort/speed 明细；仍是 Draft）
   143	   │ 用户完成选择（或维持 Recommended 默认）
   144	   ▼
   145	PendingCreate（Draft 态下 composer 已配置完毕，尚未提交，等待首条消息）
   146	   │ 用户发送首条消息 → 原子 createSession(config.model=<编码结果>)+send()
   147	   ▼
   148	CommittedToSession（该值已写入 SessionHandle 所在的这一次 createSession 调用，

   131	## 4. 状态机（写作纪律优先项）
   132	
   133	### 4.1 额度/用量数据刷新状态机
   134	
   135	驱动：D1 `queryBilling(session, window?)` 返回 `Promise<SessionBillingSnapshot>`（D1 §7，confirmed）；`fetchedAt` 字段决定"新鲜度"判断。
   136	
   137	```
   138	Idle（未查询过 / 首次进入卡片）
   139	  │ 用户打开额度/用量卡片，或 UI 定时刷新触发
   140	  ▼
   141	Fetching（await queryBilling() 进行中）
   142	  │
   143	  ├─ resolve(SessionBillingSnapshot) ──▶ Fresh（刚拿到快照，fetchedAt≈now）
   144	  │                                         │ 经过 UI 自定义的"新鲜度阈值"（D5 设计决策，非协议规定）
   145	  │                                         ▼
   146	  │                                      Stale（仍展示上次快照数值，但新鲜度提示变为"X 分钟前"）
   147	  │                                         │ 下一次刷新触发
   148	  │                                         └──▶ 回到 Fetching
   149	  │
   150	  └─ reject('billing_query_subject_unresolved') ──▶ FetchFailed（见 §4.4，不得展示零值快照）
   151	```
   152	
   153	**注意**：D1/D2 没有定义"用量刷新"的协议层触发事件（不像 `CapabilityChangedEvent` 有专门的 wire type）——刷新节奏（轮询间隔、是否在打开卡片时才查询）完全是应用层自行决定，D5 需在实现阶段自行设计，本状态机只锚定"数据从哪几个协议状态转移过来"。
   154	
   155	### 4.2 超限状态机
   156	
   157	**协议诚实缺口标注**：D1 `KernelEvent` 11 类判别联合里**没有**"配额耗尽"专属事件类型（同 foundation §3.2 Goal 缺口的同款问题）——超限的判定完全依赖 UI 自行比较 `SessionBillingSnapshot.requestCount` 与 `totalQuota`，不存在协议层的"超限推送"。
   158	
   159	```
   160	Normal（requestCount / totalQuota 低于 D5 自定阈值，如 80%）
   161	  │ 下次刷新，比值超过阈值
   162	  ▼
   163	Approaching（额度接近上限，UI 显示提醒色，composer 仍可用）
   164	  │ 下次刷新，requestCount ≥ totalQuota
   165	  ▼
   166	Exceeded（额度耗尽）
   167	  │
   168	  ├─ Codex 参照（T-021 §5.2，confirmed）：Codex 是软限流——超出 5h/weekly 窗口后请求变慢或需等待，
   169	  │   并非硬阻断；Credits 可扩展用量。**直接仿 codex**：D5.4 呈现层面同样不建议在超限时强制阻断
   170	  │   composer——这是 D5 设计决策，非 D1 协议要求（D1 层面 send() 本身不检查配额，`session_locked`
   171	  │   等既有拒绝码里也没有"配额不足"这一项）。
   172	  │
   173	  └─ 若目标部署要做硬阻断（企业侧策略），需要应用层自行在 composer 提交前插入配额检查——
   174	      **这不是 D1/D2 保证的能力**，若做，属于 D5/Server 自建逻辑，须在实现阶段显式声明，
   175	      不得暗示这是内核原生拒绝。
   176	```
   177	
   178	### 4.3 `billingAttribution` 声明分支（部署时静态值，非运行时转移，但决定 UI 呈现走哪条分支）
   179	
   180	严格讲这不是一个会在运行时发生转移的状态机（D1 §4.1 明确"部署时确定的静态事实，通常整个部署实例内所有 session 取值一致"），但因为它直接决定 L2/L3 两套完全不同的呈现路径，写作纪律要求同样显式列出：
   181	
   182	```
   183	部署阶段声明（一次性，不随 session 变化）
   184	  ├─ 'session'（C-3 验证通过、per-session 换 key 已配置）
   185	  │     └─▶ **仅满足 L3 的必要条件之一，非充分条件**（**v2.2 收残：T-024 F-02**，消解本图
   186	  │         此前"UI 可展示本会话成本"这一过度表述与 §2.4 正文的矛盾）——`SessionBillingSnapshot`
   187	  │         本身仍只有 `requestCount`/`totalQuota`/`rpm`/`tpm`/时间窗字段，没有 token/金额/
   188	  │         币种，**不得**仅凭这一分支成立就宣称"UI 可展示本会话成本"；真正展示"本会话成本"
   189	  │         还需 §2.4 依赖枚举第 1 项（D3 `usage_ledger` 提供 Chat/Turn 关联键+计价字段）同时
   190	  │         就位，两项缺一均不可行，L3 仍完全分期
   191	  │
   192	  └─ 'user_tenant_aggregate'（C-3 不成立，或部署未做这项工程量——本页明确标注：截至目前 C-3 未验证，
   193	       应假设当前处于此分支）
   194	        └─▶ UI 只能展示租户/用户聚合用量；**不得**声称能拆到单 Chat；
   195	            §3 归因降级提示卡片即对应此分支
   196	```
   197	
   198	**通过 `CapabilityChangedEvent` 感知变化**：若部署配置变更导致 `billingAttribution` 值改变（罕见，理论上需要重新部署/重新握手），UI 通过 D1 `CapabilityChangedEvent`/D2 `evt.capability_changed`（foundation §5.1 第 9 行）感知，并以完整能力快照替换本地缓存——同 foundation 已有结论，本页不重复展开。

   200	### 4.4 `queryBilling` 查询失败呈现状态机
   201	
   202	```
   203	Requesting（await queryBilling()）
   204	  │
   205	  ├─ 成功 resolve ──▶ 按 §4.1 Fresh/Stale 正常渲染快照
   245	| `succeeded` | hard abort+resend 均完成；stop 正常完成 | "已中断并重新开始" / "已停止" | — |
   246	| `submitted`（仅 soft steer） | RPC 被接受，**不承诺**消息确实注入 active run | "已提交转向请求" | **不得**呈现为"已成功打断"——D1 明确这是结构性不可观察边界，措辞必须诚实（D1 §6.1(a)） |
   247	| `aborted_no_resend` | 存在可抢占窗口下 stop 抢先，resend 被丢弃 | "已中止，未重新发送" | 仅 hermes 与 openclaw runId 定向路径可靠，openclaw 单 RPC 路径不适用（D1 §9.3 F-08 范围校正） |
   248	| `aborted_resend_failed` | abort 确认生效但 resend 自身失败 | "已中止旧内容，但重试发送失败" | openclaw 上仅在 error 响应体透出可判读信号时才可靠（D1 §11 C-4 待验） |
   249	| `aborted_effect_unknown` | abort 是否生效本身不可判定 | **必须**呈现为"状态不确定"，**不得**暗示"已中止"或"仍在运行" | D1 §6.1(b) 强制性要求：调用方不得据此推断旧 run 状态，需主动重新查询；这是 D5.1 措辞设计里最容易出错的一格 |
   250	| `rejected` | abort/cancel 从未生效（同步失败） | "操作被拒绝" | 收窄后不再涵盖"无法区分"的场景，那类走 `aborted_effect_unknown` |
   251	| `timed_out` | 等待内核确认超时 | "等待响应超时" | — |
   252	
   253	`SessionLockState`（`idle`/`send_pending`/`interrupt_in_progress`/`stop_in_progress`，D1 §9.3）驱动 composer/操作按钮的可用性：例如 `send_pending` 期间应禁用第二次发送（避免触发 `session_locked` 拒绝码）。

   239	
   240	### 7.1 createSession 门控与租户/坐席上下文注入
   241	
   242	引 [[d5-00-foundation]] §5.2：`createSession` 驱动子面标注为"**D5.2**（新建 Chat）+ **D5.6**（`billing.tokenRef` 铸造，租户/坐席上下文注入）"。具体到 D1 契约（confirmed）：
   243	
   244	- `createSession` 步骤 0（v3.3 新增前置校验）：若该内核部署实例的 `billingAttribution` 为 `'user_tenant_aggregate'` 且 `config.newapiEndpoint.deploymentTokenRef` 未提供，**同步拒绝** `aggregate_billing_requires_deployment_token`。
   245	- 步骤 2：为该 session 铸造专属计费 token，写入 `SessionHandle.billing.tokenRef`。
   246	
   247	**D5.6 呈现含义**：新建 Chat 这个动作在协议层可能因为**部署配置问题**（而非用户的 License/坐席状态问题）而失败。§4.2 的阻断态（`expired`/`revoked`/`suspended`）与这里的 `aggregate_billing_requires_deployment_token` 是**两类完全不同的错误**，不能用同一套文案：
   248	
   249	| 错误来源 | 用户能否自行解决 | D5.6 呈现建议 |
   250	|---|---|---|
   251	| License/坐席状态阻断（§4.2/§6.3） | 部分可以（续费/联系管理员） | 明确的账号/坐席状态提示 |
   252	| `aggregate_billing_requires_deployment_token` | **不能**——这是部署配置缺失，foundation §5.2 已明确"不应期望终端用户 UI 能自行修复" | 展示为系统/部署级错误，引导"联系管理员"或指向 Console 诊断信息，**不得**呈现为"你的 License 有问题" |

   254	### 7.2 billingAttribution 对本页的影响
   255

   207	### 3.3 终结路径：`stop()` vs `SessionEndEvent`（两条独立路径，均需呈现）
   208	
   209	**主动路径**：用户发起 `stop()`，其 `OperationOutcome` 三态子集（`succeeded`/`timed_out`/`rejected`，D1 §2.5，confirmed）决定 Chat 是否真正进入 `Stopped`：
   210	- `succeeded` → Chat 进入 `Stopped{reason:'stopped'}`。
   211	- `timed_out`/`rejected` → **D1 未终结该会话**，列表项应维持此前状态，不得擅自标记为 Stopped（措辞沿用 [[d5-00-foundation]] §5.4 对应行，本页不重复定义新文案）。
   212	
   213	**被动路径**：内核侧主动上报 `SessionEndEvent`（D1 §3/D2 `SessionEndPayload`，confirmed），`reason` 字段四值决定 UI 措辞差异——**这四个 reason 值语义不同，不应统一呈现为"已停止"**：
   214	
   215	| `SessionEndEvent.reason` | 含义 | D5.2 呈现建议 |
   216	|---|---|---|
   217	| `stopped` | 与用户主动 `stop()` 对应（旁路镜像） | "已停止"，与主动路径一致 |
   218	| `kernel_exited` | 内核进程退出（非用户发起） | **不得**呈现为"已停止"——应标注"内核已退出"，提示这是非预期终结，可能需要用户判断是否重试/排查，而非当作正常收尾 |
   219	| `transport_closed` | 连接层关闭 | 应标注"连接已断开"，与内核仍在运行但暂不可达区分——不应暗示会话内容已丢失 |
   220	| `error` | 错误终结 | 应标注"因错误终结"，链接至 D5.1 内联错误呈现（不重复定义错误文案本身） |
   221	
   222	这是本页在 D1/D2 已确认字段基础上的**如实展开**（D1/D2 confirmed 字段本身；四态各自对应的 UI 措辞是 D5 设计决策，T-021 未给出对应产品文案，foundation 也未展开到这一粒度）。

   224	### 3.4 关键差异：openclaw 原生删除 vs hermes 仅中断——诚实缺口标注
   225	
   226	**这是本页在阅读 D1 §5 Transport 映射表时发现的一处对"会话生命周期终结后能否恢复"有直接影响、且未被 foundation 展开的细节**，本页在此如实标注：
   227	
   228	- **openclaw**：`stop()` 映射为两步非原子序列——`sessions.abort`/`chat.abort`（确认 `turn_complete` 或超时）→ `sessions.delete`（D1 §5 Transport 映射表，confirmed）。也就是说 **openclaw 的 `stop()` 会导致内核原生会话被真正删除**，靠 D1 §6.3"已 stop 黑名单"机制兜底非原子窗口期的一致性。
   229	- **hermes**：`stop()` 对应 ACP `cancel(session_id)`，**只中断当前 prompt，不销毁持久会话**——持久删除需要走 CLI `hermes sessions delete`，这是 D1 `stop()` 方法本身**未覆盖**的独立操作（D1 §5 Transport 映射表，confirmed）。
   230	
   231	**这一差异叠加 openclaw "resume-after-delete" 语义未经确认**（D1 §2.1 resume 校验注释、§12 开放问题第 4 条，标注为 ❓ 未能确认，来源 [[kernel-ecosystem-facts]]；D1 当前**保守按 reject 处理**，不假设可自动重建）——意味着：
   232	
   233	> 同样一次"停止"操作（UI 上是同一个按钮、同一次 `stop()` 调用），在 openclaw 后端下大概率导致该 Chat **事实上不可恢复**（原生会话已删除，resume 是否重建未确认，D1 保守拒绝），在 hermes 后端下持久会话**可能仍然存在**（`stop()` 本身不删除），恢复的可行性取决于该内核部署的 `sessionResume` 能力声明。
   234	
   235	**这与 D1 INV-1（透明性）如何共存**：INV-1 要求 UI 不得对内核类型做分支判断（[[d1-kernelport-spec-v3-5]] §1）。本页的结论是：**UI 确实不应该、也不能对 openclaw/hermes 分别设计"恢复"交互**——唯一暴露给 UI 的、合规的信号是 `capabilities().sessionResume`（boolean，见 §3.6）。但这也意味着：**当 `sessionResume:false` 时，UI 侧完全无法向用户解释"为什么这个 Chat 不能恢复"是因为内核类型差异**，只能呈现一个笼统的"该会话不支持恢复"提示——这是 INV-1 透明性换来的代价，本页认为需要显式记录，而不是留给实现阶段自己发现。子面实现时不应尝试绕过 INV-1 去为两种内核设计不同的恢复文案。

   237	### 3.5 归档（Archive）——与运行态正交的 UI 组织标记，非 D1 概念（v2 修复：消解 T-023 F-06）
   238	
   239	**诚实缺口**：D1/D2 全文没有"archive"概念，`SessionHandle` 没有对应字段——archive/取消 archive 是纯应用层（P7 Server）对 Chat 元数据的一个布尔标记操作，不触发任何 D1 方法调用，也不隐含"该会话已 stop"。
   240	
   241	**权威语义（v2 修复，取代 v1 版本"archive 只能从 Stopped 进入"的状态图与"archive 与底层生命周期正交"这段文字两处自相矛盾的表述）**：`archived` 是与 §3.1 状态图中 `Active`/`Stopped` 等**运行态正交**的独立布尔轴——是纯粹的 UI 组织标记（"货架"），不是运行态状态机上的一个节点：
   242	
   243	- **任意运行态的 Chat 均可被 archive**，包括仍处于 `Active`（甚至 `send_pending`/`interrupt_in_progress` 等子态）的 Chat——archive 操作本身只是把它从默认可见列表隐藏，**不触发、也不影响** `stop()`：底层 `SessionHandle` 继续存在、继续可以 `send()`、继续产生 `TurnCompleteEvent`/`ApprovalRequestEvent`/`SessionEndEvent` 等全部协议事件。
   244	- **archived 期间的通知义务（v2 新增，回应 T-023 对"隐藏运行中会话缺通知设计"的指出）**：即使 Chat 已被 archive、从默认列表隐藏，若其底层 session 仍是 `Active` 并产生了新的 `TurnCompleteEvent`（回合完成）或 `ApprovalRequestEvent`（新审批到达），D5.2 仍需向用户呈现某种非侵入式提醒（如"已归档会话中有更新"的全局/Archived 分区徽标）——**不得**因为 UI 隐藏就静默丢弃这些事件的呈现义务，否则用户可能对一个仍在消耗额度/等待审批的会话完全失去感知。具体徽标像素本页不展开，只要求这条纪律不被忽略。
   245	- **取消 archive 恢复到 archive 前的实际运行态**，不强制降级为 `Stopped`——若被 archive 的 Chat 底层仍是 `Active`，取消 archive 后应直接回到 `Active`（可能已经是不同的子态，取决于 archive 期间的实际协议事件），而不是像 v1 版本状态图那样统一回退到"未归档但已终结态"。

    59	## 2. Turn：一次 `send()` 的生命周期状态机
    60	
    61	**D5 设计决策（重要澄清）**：D1/D2 本身**没有**一个字面命名为「Turn 状态机」的枚举类型——`send()` 只返回 `{runId}`（[[d1-kernelport-spec-v3-5]] §2.2），Turn 是否「仍在运行」是 D5 依据「该 `runId` 尚未收到 `TurnCompleteEvent`」这一事件到达顺序自行推断的产品层状态，不是 D1 暴露的显式查询字段（D1 没有「query active run」方法）。下面的状态机是 D5 把 `send()`/事件流/`SessionLockState`（[[d1-kernelport-spec-v3-5]] §9.3）三者合成后的呈现层状态机，需要与 §9.3 的锁状态严格区分开——两者不是同一回事（下方专门澄清）。
    62	
    63	```
    64	IDLE（无未决 runId，composer 可发送）
    65	  │ 用户点击发送 → send()
    66	  ▼
    67	SUBMITTING（等待 res.send() ack；D1 SessionLockState=send_pending，
    68	             极短窗口，正常情况几乎不可感知，见 D1 §9.3 表首行）
    69	  │ res.send({runId}) 返回
    70	  ▼
    71	RUNNING（SessionLockState 已回落 idle——send() 的 Promise 完成不代表
    72	         agent 已经跑完，只代表这次 RPC 往返本身成功；D5 以
    73	         「该 runId 尚未出现 TurnCompleteEvent」判定仍在 RUNNING，
    74	         期间持续渲染 message.delta / thinking / tool_call / tool_result /
    75	         approval_request / error 等 Item，seq 仅保证同一 runId 内排序，
    76	         不承诺跨 run 单调，见 [[d1-kernelport-spec-v3]] KernelEventBase.seq 注释）
    77	  │                                            │
    78	  │ 用户发起 interrupt()/stop()                 │ 内核直接产出 TurnCompleteEvent
    79	  ▼                                            │（stopReason: completed/error/max_turns）
    80	INTERRUPTING（SessionLockState 转 interrupt_in_progress/                │
    81	              stop_in_progress，三条 mode 子状态机见 §5）                │
    82	  │ operation 终态化 + TurnCompleteEvent 到达                            │
    83	  ▼                                                                     ▼
    84	RESOLVED（TurnCompleteEvent.stopReason 摘要展示，运行状态条落定，
    85	          composer 恢复可发送）
    86	  │
    87	  ▼
    88	回到 IDLE（等待下一次 send()）
    89	```
