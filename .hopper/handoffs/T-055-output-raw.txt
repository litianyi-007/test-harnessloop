+**坑 1（`[实测]`）：普通（非 editable）install 仍会在 submodule 里留下 `build/` 目录。**
+`uv pip install <path>`（哪怕不带 `-e`）触发 setuptools 的标准 build 流程时，会在**源码目录本身**
+（不是 venv、不是 scratchpad）创建 `build/bdist.*` + `build/lib/*` staging 目录（entire 源码树拷了一份
+进去）。这不是 editable install 才有的 egg-info 问题，是 `[tool.setuptools]` 这类项目的构建产物落点
+默认就是源码目录旁边。**装完必须 `rm -rf kernels/hermes/build` 并核对 `git status` 干净**——本轮已
+如此清理，`build/` 未被跟踪（不在 `.gitignore` 里也没关系，因为从未 commit，`git status --porcelain`
+清空后确认过）。
+
+**坑 2（`[实测]`）：任何不带 `HERMES_HOME` 的 `hermes` CLI 调用都会碰用户全局 `~/.hermes`。**
+本轮最初跑 `hermes --help`/`hermes gateway --help` 这类看起来"只读、不会有副作用"的命令时，**没有**
+显式设置 `HERMES_HOME`，结果在 `~/.hermes/logs/` 下创建了两个空文件（`agent.log`/`errors.log`，
+0 字节，见 `hermes_constants.py:56-64` `HERMES_HOME` 解析逻辑——未设时落到平台默认 `~/.hermes`）。
+影响面很小（只有两个空日志文件，没有 config.yaml/state.db/凭证），但这是一个真实的隔离缝隙，已发现并
+清理（`rm -rf ~/.hermes`，清理前确认目录内容全部是本轮新建的空文件）。**教训：隔离 recipe 里的每一条
+`hermes` 命令都要显式带 `HERMES_HOME`，包括看起来无害的 `--help`。** 类比 openclaw recipe 里记录的

+## 5. per-session key 机制的源码坐实（零改动路径）
+
+请求发到 `/v1/chat/completions`，body 里的 `"model"` 字段就是 alias 名（不是真实要打的模型名）：
+
+1. `_resolve_route(model_alias)`（`[源码]` `gateway/platforms/api_server.py:1795-1799`）在
+   `self._model_routes`（gateway 启动时由 `_parse_model_routes(extra.get("model_routes"))` 解析，
+   `[源码]` `:1037-1039` 构造函数里调用）里查 alias，命中则返回该条目的
+   `{model, provider?, api_key?, base_url?}`。
+2. 三处 HTTP handler 都在派发前调用这个方法：`:2863`（responses 路径）、`:3983`
+   （chat/completions 路径）、`:5025`（sessions chat 路径）。
+3. 拿到 `route` 后，在 `_run_agent`（构造 `AIAgent` 之前）里：
+   - `route.get("model")` → 覆盖 `model`（`:1905`）
+   - `route.get("api_key")` → 覆盖 `runtime_kwargs["api_key"]`（`:1910`）
+   - `route.get("base_url")` → 覆盖 `runtime_kwargs["base_url"]`（`:1912`）
+   - 若还给了 `route.get("provider")`（本轮未用），额外重新解析该 provider 的凭证链（`:1889-1901`）
+   - 这一整段判断的前提是 `route and not session_override`（`:1885-1888`）——只有当会话没有显式
+     `/model` 覆盖时，route 配置才生效，符合"静态路由是默认值、用户显式操作优先"的直觉
+4. 最终 `AIAgent(model=model, **runtime_kwargs, ...)`（`:1930` 附近）拿到的就是这一路由专属的
+   `api_key`/`base_url`——**这条链路里没有任何一步碰 `kernels/hermes` 源码，是配置驱动的既有生产
+   代码路径**，PRE-① 报告 §2.4 的判定在本轮 e2e 里精确复现。

    60	
    61	| # | 断言 | 判定 | 源码证据 |

    64	
    65	**证据链（同 run 软注入，即 D1 所谓 "soft steer"，在 hermes 上确凿存在且已接入生产路径）**：
    66	
    67	1. `run_agent.py:2899-2933` `AIAgent.steer(text) -> bool`：docstring 原文 ——
    68	   > "Inject a user message into the next tool result without interrupting. Unlike interrupt(), this does NOT stop the current tool call. The text is stashed and the agent loop appends it to the LAST tool result's content once the current tool batch finishes."
    69	   这正是 openclaw `queueMode:"steer"` 的同类语义：**不中断当前执行，把引导文本注入下一次工具结果**。
    70	2. 这不是孤立/未接线的方法：`agent/tool_executor.py:1035,1048,1102,1720,1761,1818` 六处调用点 `agent._apply_pending_steer_to_tool_results(messages, ...)`，在工具执行返回后把 pending steer 文本真正拼进 tool result——是已布线进主执行循环的生产代码，不是死代码或测试桩。
    71	3. **ACP 侧确实暴露了它**：`acp_adapter/server.py:1989-2006` `_cmd_steer`：当 `state.is_running and hasattr(state.agent, "steer")` 时调用 `state.agent.steer(steer_text)`，返回 `"⏩ Steer queued for the active turn: ..."`；触发方式是把 `/steer <text>` 作为普通文本发进 ACP `prompt()`（`server.py:1335-1354` 对空闲会话做了专门的降级重写逻辑，明确区分"有 active run 时走真正的软注入"与"空闲时退化为普通 prompt"两条分支）。
    72	4. **不是 ACP 独有的边角能力**：CLI 侧同款命令 `hermes_cli/commands.py:112` `CommandDef("steer", "Inject a message after the next tool call without interrupting", "Session", ...)`；messaging Gateway 侧 `gateway/run.py:5443-6017` 一整套 `effective_mode == "steer"` 分支（`can_steer`/`steered` 变量、`running_agent.steer()` 调用），说明这是横跨 CLI / Gateway / ACP 三个入口的**一等公民能力**，而非 ACP 专属 hack。

    74	**对 D1 的影响**：D1 v3.5 §11 C-5 原本把"hermes ACP 是否具备任何形式的同 run 软注入机制"列为**非阻塞性验证项**，并预先写好了条件规则——"若确认存在：`capabilities().interruptModes` 对 hermes 放宽为包含 `'steer'`，不视为对本 spec 的推翻，是能力协商模型天然支持的正常扩展"（v3.5 line 743）。本次源码核验的结果正是"确认存在"，**按 D1 自己的规则应该触发这条放宽**：hermes 的 `capabilities().interruptModes` 不应再对 `'steer'` 恒为空，`interrupt(mode:'steer')` 不应恒 reject。这不需要改 hermes 一行代码——只需要 KernelPort 适配器把 `interrupt(session,{mode:'steer',text})` 映射为「向 ACP 发一条 `/steer <text>` 的 `prompt()` 调用」，且仅在 `state.is_running` 时才是真软注入（空闲时 hermes 自己会降级为普通 prompt，适配器应据此把空闲态的 steer 请求也归类为"降级"而非"拒绝"）。

   107	## 2. 问题二（C-3）：hermes 是否原生支持 per-session LLM 出口 baseUrl/key
   108	
   109	**判定：原生支持——但支持它的不是 D1 目前唯一考虑的 ACP 传输线路，而是 hermes 自己的 `gateway/platforms/api_server.py` 平台的 `model_routes` 特性。倾向 path①（session 级归因可行），不必退化到 path②（部署级聚合）。** 分三层证据说明：
   110	
   111	### 2.1 全局/部署级默认配置（这一层确实是共享的，印证 D1 v3.2 §2.1 注释"baseUrl 是租户/环境级配置"没错）
   112	
   113	`cli-config.yaml.example:8-46`：`model.provider`/`model.base_url`/`model.api_key`（或 `.env` 里的 `OPENROUTER_API_KEY` 等）是单一部署的默认凭证，所有 session 共享——这部分和设计假设一致。
   114	
   115	### 2.2 Python/AIAgent 库层：per-instance 原生支持（属实，证据最直接）
   116	
   117	`run_agent.py:423-429` `AIAgent.__init__(self, base_url: str = None, api_key: str = None, provider: str = None, ...)`——**每个 AIAgent 实例都可以独立传入 base_url/api_key**。ACP 的每个 session 本来就对应一个独立的 `AIAgent` 实例（`acp_adapter/session.py:199-205` `create_session` → `_make_agent` → `AIAgent(**kwargs)`），所以"per-session 不同出口"在对象模型层面从来没有被禁止过。
   118	
   119	再往下一层，`hermes_cli/runtime_provider.py:1522-1528` `def resolve_runtime_provider(*, requested=None, explicit_api_key=None, explicit_base_url=None, target_model=None)`——**凭证解析函数本身已经支持"显式覆盖"参数**，这不是要新写的能力，是已经存在但当前 ACP 适配器没有调用到的能力。
   120	
   121	### 2.3 ACP 适配器目前的实际接线（缺口所在）
   122	
   123	`acp_adapter/session.py:590-648` `_make_agent(...)` 调用 `resolve_runtime_provider(requested=requested_provider or config_provider)`——**没有传 `explicit_api_key`/`explicit_base_url`**，即便这两个关键字参数在下游函数里现成可用。`acp_adapter/server.py` 的 ACP 方法里，`new_session`（`server.py:1113-1131`，仅接受 `cwd, mcp_servers`）与 `set_session_model`（`server.py:2022-2054`，`model_id` 经 `_resolve_model_selection` 解析为"已配置的 provider 名 + model"，不是任意内联 base_url/key）**都不接受调用方传入的裸 baseUrl/key**——这是 ACP 协议层面目前确实存在的缺口，直接对应 D1 §11 C-3 的疑虑。
   124	
   125	但**已有一个天然的、无需改协议 schema 的挂载点**：`server.py:2072-2090` `set_config_option(config_id, session_id, value)` 是一个已经存在的、通用的 key-value 配置写入 RPC，当前实现是"接受任意 config_id 存进 `state.config_options`"（`server.py:2081-2089`），但**这些值目前没有被 `_make_agent` 读回**。把 `_make_agent` 改成读取 `state.config_options.get("baseUrl")`/`get("apiKey")` 并透传给 `resolve_runtime_provider(explicit_api_key=..., explicit_base_url=...)`，是一个**局部小 patch**（预计 <50 行，两个文件：`session.py` 加两个可选参数直传、`server.py::set_config_option` 或 `_make_agent` 调用处读取 `state.config_options`），不涉及 ACP 协议本身的 schema 变更（`set_config_option` 早已是通用透传通道）。
   126	
   127	### 2.4 更强的原生证据：`gateway/platforms/api_server.py` 的 `model_routes`（零 patch 路径）
   128	
   129	这是本轮最重要的补充发现。hermes 自带的 OpenAI 兼容 HTTP 网关平台**原生支持"per-alias 独立 upstream 凭证"**：
   130	
   131	- `gateway/platforms/api_server.py:1024-1037`（docstring + 解析代码）：
   132	  ```
   133	  model_routes: maps incoming `model` field values to specific
   134	    model_routes:
   135	      <alias>:
   136	        model: "..."
   137	        provider: "..."          # optional — per-route UPSTREAM provider
   138	        api_key: "sk-…"          # optional — per-route UPSTREAM provider
   139	        base_url: "https://…"    # optional — per-route base URL override
   140	  ```
   141	- `gateway/platforms/api_server.py:1900-1913`：客户端请求里的 `model` 字段被解析成 `route`，`route.get("api_key")`/`route.get("base_url")` 直接写入 `runtime_kwargs["api_key"]`/`runtime_kwargs["base_url"]`，最终传给 `AIAgent(**runtime_kwargs)`——**这条链路完整闭合，是生产代码，不是设计草稿**。
   142	- 结合 `/v1/runs`、`/api/sessions/{id}/chat` 等有状态会话接口（见 §1.6 第 15 条），客户端在每次请求/每个 session 里指定不同的 `model` 别名，就能让**不同 session 落到不同的 newapi baseUrl + key** 上——这正是 D1 §7 注入链契约第④步需要的能力，且是 hermes **已经实现、无需改一行源码**的路径，前提是这些 alias 在 `model_routes` 配置块里预先登记（配置时静态登记，不是运行时任意动态下发——这一点和"任意 session 现铸现用"之间还有一步之遥，但比 ACP 路径成熟得多）。
   143	
   144	### 2.5 判定小结
   145	
   146	| 路径 | 是否原生支持 per-session baseUrl/key | 改动量级 |
   147	|---|---|---|
   148	| 全局默认（`cli-config.yaml`/`.env`） | 否，本就是共享层 | — |
   149	| Python `AIAgent` 库嵌入 | **是**（构造参数直接支持） | 无需改 |
   150	| `gateway/platforms/api_server.py`（`model_routes`） | **是**（原生 per-alias upstream key/baseUrl，已生产可用） | **无需改**，只需在部署配置里预注册 alias |
   151	| ACP 协议（`hermes acp` stdio） | **否（目前）**，但有现成挂载点 | **小 patch**（利用已有 `set_config_option` 回填 `_make_agent`，<50 行，不改协议 schema） |
   152	
   153	**对 D1 的建议**：C-3 不必默认走"验证不可行 → 退化到 `user_tenant_aggregate` 聚合计费"的悲观分支。只要 app 侧愿意接受"走 `api_server` HTTP 平台而非 ACP 作计费敏感场景的传输线路"，或者接受给 ACP 打一个几十行的小 patch，`billingAttribution: 'session'` 都是可以真实达成的，不是无法验证的假设。

   157	## 3. 问题三：改动可能性总评
   158	
   159	**不需要 fork hermes，也不需要对其做实质性改动（无中改/大改）。** 分层给出量级：
   160	
   161	- **无需改**：ACP 会话生命周期（new/load/resume/fork/list/cancel）、审批桥接（allow_once/allow_session/allow_always/deny + fail-closed 超时）、per-profile 工具集裁剪（`hermes-acp` 固定集）、`interrupt(mode:'steer')` 的落地——**这条尤其值得强调：steer 已经在 hermes 里现成可用，D1 适配器只需要在自己的映射层把"发一条 `/steer <text>` 的 prompt()"接到 `interrupt(mode:'steer')` 上即可，零 hermes 改动**。
   162	- **零改动即可拿到 per-session 计费凭证隔离**：如果把 `gateway/platforms/api_server.py`（HTTP，`/v1/runs` 系列）而非 `hermes acp`（stdio ACP）当作面向 newapi 计费场景的传输线路，`model_routes` 特性原生支持 per-alias 独立 base_url/api_key，不需要碰源码，只需要在部署配置里按 session 池预注册若干 alias。
