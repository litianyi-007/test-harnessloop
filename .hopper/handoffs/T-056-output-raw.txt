 ## 5. per-session key 机制的源码坐实（零改动路径）
 
 请求发到 `/v1/chat/completions`，body 里的 `"model"` 字段就是 alias 名（不是真实要打的模型名）：
 
 1. `_resolve_route(model_alias)`（`[源码]` `gateway/platforms/api_server.py:1795-1799`）在
    `self._model_routes`（gateway 启动时由 `_parse_model_routes(extra.get("model_routes"))` 解析，
    `[源码]` `:1037-1039` 构造函数里调用）里查 alias，命中则返回该条目的
    `{model, provider?, api_key?, base_url?}`。
-2. 三处 HTTP handler 都在派发前调用这个方法：`:2863`（responses 路径）、`:3983`
-   （chat/completions 路径）、`:5025`（sessions chat 路径）。
+2. 三处 HTTP handler 都在派发前调用这个方法（T-055 对抗复核纠正映射错误）：
+   `_handle_chat_completions` 的 `:2863`（`/v1/chat/completions`，本轮 e2e 实测走的正是这条）、
+   `_handle_responses` 的 `:3983`（`/v1/responses`）、`_handle_runs` 的 `:5025`（`/v1/runs`）。
+   **`/api/sessions/{session_id}/chat`**（`_handle_session_chat`，`gateway/platforms/api_server.py:
+   2550-2575`）调用 `_run_agent` 时**不解析、也不传入 `route`**——这条路径不受 `model_routes`
+   覆盖，**不在**本轮 e2e 闭合范围内，不要把"api_server 三个主 HTTP 入口都覆盖"误读成
+   "api_server 下所有端点都覆盖"。
 3. 拿到 `route` 后，在 `_run_agent`（构造 `AIAgent` 之前）里：
    - `route.get("model")` → 覆盖 `model`（`:1905`）
    - `route.get("api_key")` → 覆盖 `runtime_kwargs["api_key"]`（`:1910`）
    - `route.get("base_url")` → 覆盖 `runtime_kwargs["base_url"]`（`:1912`）
    - 若还给了 `route.get("provider")`（本轮未用），额外重新解析该 provider 的凭证链（`:1889-1901`）
    - 这一整段判断的前提是 `route and not session_override`（`:1885-1888`）——只有当会话没有显式
      `/model` 覆盖时，route 配置才生效，符合"静态路由是默认值、用户显式操作优先"的直觉
 4. 最终 `AIAgent(model=model, **runtime_kwargs, ...)`（`:1930` 附近）拿到的就是这一路由专属的
    `api_key`/`base_url`——**这条链路里没有任何一步碰 `kernels/hermes` 源码，是配置驱动的既有生产
    代码路径**，PRE-① 报告 §2.4 的判定在本轮 e2e 里精确复现。

   193	## 5. per-session key 机制的源码坐实（零改动路径）
   194	
   195	请求发到 `/v1/chat/completions`，body 里的 `"model"` 字段就是 alias 名（不是真实要打的模型名）：
   196	
   197	1. `_resolve_route(model_alias)`（`[源码]` `gateway/platforms/api_server.py:1795-1799`）在
   198	   `self._model_routes`（gateway 启动时由 `_parse_model_routes(extra.get("model_routes"))` 解析，
   199	   `[源码]` `:1037-1039` 构造函数里调用）里查 alias，命中则返回该条目的
   200	   `{model, provider?, api_key?, base_url?}`。
   201	2. 三处 HTTP handler 都在派发前调用这个方法（T-055 对抗复核纠正映射错误）：
   202	   `_handle_chat_completions` 的 `:2863`（`/v1/chat/completions`，本轮 e2e 实测走的正是这条）、
   203	   `_handle_responses` 的 `:3983`（`/v1/responses`）、`_handle_runs` 的 `:5025`（`/v1/runs`）。
   204	   **`/api/sessions/{session_id}/chat`**（`_handle_session_chat`，`gateway/platforms/api_server.py:
   205	   2550-2575`）调用 `_run_agent` 时**不解析、也不传入 `route`**——这条路径不受 `model_routes`
   206	   覆盖，**不在**本轮 e2e 闭合范围内，不要把"api_server 三个主 HTTP 入口都覆盖"误读成
   207	   "api_server 下所有端点都覆盖"。
   208	3. 拿到 `route` 后，在 `_run_agent`（构造 `AIAgent` 之前）里：
   209	   - `route.get("model")` → 覆盖 `model`（`:1905`）
   210	   - `route.get("api_key")` → 覆盖 `runtime_kwargs["api_key"]`（`:1910`）
   211	   - `route.get("base_url")` → 覆盖 `runtime_kwargs["base_url"]`（`:1912`）
   212	   - 若还给了 `route.get("provider")`（本轮未用），额外重新解析该 provider 的凭证链（`:1889-1901`）
   213	   - 这一整段判断的前提是 `route and not session_override`（`:1885-1888`）——只有当会话没有显式
   214	     `/model` 覆盖时，route 配置才生效，符合"静态路由是默认值、用户显式操作优先"的直觉
   215	4. 最终 `AIAgent(model=model, **runtime_kwargs, ...)`（`:1930` 附近）拿到的就是这一路由专属的
   216	   `api_key`/`base_url`——**这条链路里没有任何一步碰 `kernels/hermes` 源码，是配置驱动的既有生产
   217	   代码路径**，PRE-① 报告 §2.4 的判定在本轮 e2e 里精确复现。

   221	## 6. 已知隔离缝隙（诚实记录，非阻断项）
   222	
   223	- **`~/.hermes/logs/` 边界泄漏**（见 §1 坑 2）：任何不带 `HERMES_HOME` 的裸 `hermes` 调用都会摸到
   224	  用户全局家目录，哪怕只是 `--help`。本轮已发现两个空日志文件并**精确清理**（前置校验确认
   225	  `~/.hermes` 内没有 config.yaml/state.db/sessions/ 等既有用户状态，只删本轮产生的 0 字节
   226	  `agent.log`/`errors.log`，目录清空后才 `rmdir`——**不是** `rm -rf ~/.hermes`，那样在复用场景下
   227	  可能连带删掉宿主机既有用户数据；具体脚本见 §7）。**后续复用本 recipe 时，每一条 `hermes ...`
   228	  命令前都应显式 `export HERMES_HOME=...` 或用 `HERMES_HOME=... hermes ...` 内联形式，不留任何
   229	  窗口期。**
   230	- **`build/` + `hermes_agent.egg-info/` 构建产物**（见 §1 坑 1）：`uv pip install <源码路径>`
   231	  （非 editable）仍会在源码目录里同时留下 `build/` 和 `hermes_agent.egg-info/`——后者被
   232	  `.gitignore:59` 遮蔽，普通 `git status` 看不到。装完必须 `rm -rf` 两者，并且核对同时用
   233	  `git status`（tracked）**和** `git status --ignored --short`（ignored）两条命令确认干净，
   234	  才算隔离达标；只查前者会漏看 egg-info 残留（T-055 对抗复核现场即抓到这个漏洞）。
   235	- **model_routes 是静态配置**（见 §0 结论）：新增一个 per-session alias 需要重启整个 gateway
   236	  进程；`gateway/platforms/api_server.py:5619` 注释里的 `/platform resume api_server` 只是端口
   237	  绑定失败（`EADDRINUSE`）后的恢复手段，`gateway/slash_commands.py:1204-1237` 显示 `/platform
   238	  resume` 只对已进入 `_failed_platforms` 且处于 paused 状态的平台生效——正常 connected 的
   239	  `api_server` 执行它会直接返回"nothing to resume"，**不能**用来热加载新增的 model_routes
   240	  alias（T-055 对抗复核纠正：recipe 早期版本误将这条端口恢复路径当成配置热重载手段）。这不是
   241	  hermes 的缺陷，是 PRE-① 报告已预告的"配置时静态登记 vs 运行时任意下发"之间的既有差距，本轮
   242	  e2e 的作用是坐实"静态登记这条路径本身能不能打通到真实计费归因"，答案是能。

   166	### B.3 new-api `/api/log/` 归因核对（逐字段）
   167	
   168	`GET /api/log/?p=0&page_size=10`（root Management API）返回的相关条目：
   169	
   170	| log id | token_name | token_id | model_name | channel_name | completion_tokens | prompt_tokens(log) | cache_tokens(other) | prompt_tokens(log)+cache_tokens |
   171	|---|---|---|---|---|---|---|---|---|
   172	| 45 | sg7-hermes-session-a | **4** | kimi-for-coding | kimi-coding | **22** | 244 | 11264 | **11508** |
   173	| 46 | sg7-hermes-session-b | **5** | kimi-for-coding | kimi-coding | **15** | 244 | 11264 | **11508** |
   174	
   175	逐字段断言：
   176	- **token 归因正确**：请求 A（alias `session-a`）的计费精确落在 `token_id=4`/`token_name=
   177	  sg7-hermes-session-a`；请求 B（alias `session-b`）精确落在 `token_id=5`/`token_name=
   178	  sg7-hermes-session-b`——**没有交叉、没有聚合到同一个 token**，这是本轮要证明的核心断言。
   179	- **model 归因正确**：两条日志 `model_name` 均为 `kimi-for-coding`，与 route 配置的
   180	  `route.model` 一致，且 new-api 侧渠道正确路由到 `kimi-coding` channel（真实 Kimi 上游）。
   181	- **usage 与响应精确吻合**：`completion_tokens` 逐条精确相等（A: 22=22，B: 15=15，都是
   182	  hermes 响应体自报的数字，不是估算）。`prompt_tokens` 表面上不直接相等（hermes 报
   183	  11508，new-api log 只报 244）——差额精确等于该条日志 `other` 字段里的
   184	  `cache_tokens:11264`（new-api 把 hermes 发来的长 system/tool prompt 命中的部分算作
   185	  prompt-cache 命中、拆开计费统计，`244(未命中)+11264(命中)=11508`，与 hermes 侧
   186	  `prompt_tokens` **精确相等**，两条日志（A/B）都是如此）——这不是巧合，是 new-api 
   187	  Claude-Messages 兼容层的标准计费字段拆分（`other.usage_semantic:"anthropic"`），
   188	  证明这两条日志确实就是对应这两次 hermes 调用的真实计费记录，不是碰巧数字接近。
   189	- 两条日志的 `request_path` 均为 `/v1/chat/completions`，`request_id` 各不相同（
   190	  `...qFuKbCAJ` / `...dMzfUoEd`），`created_at` 时间戳与两次 curl 调用发起时间吻合，
   191	  `is_stream:true`（hermes 内部对上游走的是流式请求，即便对外 `/v1/chat/completions`
   192	  这次调用本身不是 stream 模式，这是 hermes→upstream 内部实现细节，不影响归因结论）。
   193	
   194	**结论：per-session key 归因 e2e 通过，逐字段（token_id/token_name/model_name/
   195	completion_tokens/prompt_tokens 折算后）精确吻合，无编造、无估算。**

   229	
   230	Authenticated readiness check for monitoring and control planes. It reports
