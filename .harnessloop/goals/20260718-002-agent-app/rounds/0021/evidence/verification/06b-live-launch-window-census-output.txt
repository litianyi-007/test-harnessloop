=== Window census via CGWindowListCopyWindowInfo (NOT System Events) ===
Why CGWindowListCopyWindowInfo and not System Events: this repo's own scope-lock history
(rounds/0021/scope-lock.md, "Scope-Lock 修订 v2 -> v3") documents a real prior incident where
System Events window enumeration returned 0 for EVERY app including Finder under a constrained
screen state, and that empty result was wrongly read as "the app has no window" — the corrective
finding recorded there is that CGWindowListCopyWindowInfo is not affected by that same screen
state. Reusing the established, corrected technique here instead of repeating the mistake.

$ T114-window-census 30045   (source: 06-probe-window-census.swift.txt)
RESULT totalOnScreenWindows=23
RESULT windowsOwnedByPID(30045)=1
  - windowNumber=7493 layer=0 name="Agent Shell" bounds=Optional(["X": 193, "Width": 1400, "Y": 74, "Height": 900])

Interpretation: exactly ONE on-screen, layer-0 (standard window layer) window is owned by the
AgentShell process immediately after launch — consistent with the `Window("Agent Shell", id:
MenuBarWindowFocus.mainWindowID)` single-instance scene creating exactly one window, no more. The
window's on-screen title is "Agent Shell" — the static title string I supplied to the `Window`
scene initializer — which is expected at this moment: on fresh launch with no session selected yet,
ContentView's detail pane shows `emptyDetail` (no explicit `.navigationTitle`), so the window falls
back to the Window scene's own static title rather than a dynamic one from SessionDetailView /
SessionListView. This confirms the required title parameter is not a cosmetic no-op — it renders,
non-blank — without needing to touch SessionListView's existing `.navigationTitle("会话")`, which
remains untouched and will take over once a session is selected (unchanged from before this fix).
23 total on-screen windows system-wide were visible to the query, confirming
CGWindowListCopyWindowInfo is actually returning real data in this session (not silently empty).

=== IMPORTANT CAVEAT: screen was locked — screenshot-based checks are NOT valid this session ===
I attempted a `screencapture -x` to visually confirm the MenuBarExtra icon renders and follows
dark/light menu bar inversion. The resulting image was NOT the live desktop — it was the macOS lock
screen (visible clock "Fri Aug 14, 11:56", account avatar "李天意", "Touch ID or Enter Password"
prompt). This is a live recurrence of the exact class of confound this task's own brief warns
about: a screenshot taken while the screen is locked does not show background app windows or their
menu bar items, and the only status icons visible on a lock screen (input source / battery / Wi-Fi)
are macOS's own lock-screen-level indicators, not third-party MenuBarExtra items. Concluding
"the menu bar icon isn't showing" from that image would be exactly as invalid as the original
Reduce-Transparency screenshot conflation this rework exists to fix, so I am explicitly NOT drawing
that conclusion. I stopped pursuing screenshot- or UI-automation-based verification for the rest of
this session once this was discovered, rather than manufacture further readings from an
environment I now know cannot be trusted for that purpose.
