# Feedback Policy

## Feedback Classes

| 分类 | 本 goal 的判定 |
|---|---|
| `positive` | 本轮缺陷已修，**七条 Acceptance Criteria 全部满足**（反证先红 / 主会话独立复跑 / 端到端 / 安装产物复验 / 版本 bump / 异构评审 / 记入 validation-log） |
| `neutral` | 缺陷定位清楚但未修完，或修了但端到端未验；**不得因为「单测全绿」判 positive** |
| `negative` | 修复引入回归，或反证从未变红，或评审判 REWORK 且未收敛 |
| `blocked` | 需要用户裁定、需要不可逆写、需要缺失的凭证或访问 |

**判定的锚点是 Acceptance Criteria，不是「感觉修好了」。** 本项目已多次出现
「三个绿灯全亮而任务没送到」——**绿灯不是判据，判据是判据**。

## Negative Feedback Actions

- **先复现再动手**：评审报的问题，主会话须自己复现一次。2026-08-12 实测两次：
  复现后发现**范围比评审报的更宽**（根因 (b) 两家评审都没点出）。
- **打回而不是绕过**：实现不对就退回返工，不为了推进而接受半对的修法。
  实测一次：第一版边界修复写成「替代」而非「并集」，**真实路径一度比修复前更差**。
- **收敛守卫**：同一轮内第 3 个 MUST-FIX 出现时停下来 checkpoint，不再连续返工。

## Blocked Feedback Actions

- **凭证/访问缺失** → 停下问用户，无预授权豁免。
- **不可逆写或生产写** → 永远 `write-safety-required`，任何契约都不能放宽。
- **删除/覆盖** → 不在预授权范围内；执行前必须先看目标内容，并如实报告范围。
  实测一次：用户说「删目录」，主会话查后发现目录里还有 probe 脚本与 gateway 日志，
  **主动收窄为只删含凭证的文件并说明理由**——收窄执行范围要明说，不能默默做。

## Round Decision Format

每轮收盘写 `decision.md`，除协议既有字段外，本 goal 额外要求：

- **静默失败计数**：本轮是否出现该类缺陷；连续计数当前值 / N。
- **被测插件**：本轮动了哪个（或哪几个）插件，各自版本从 → 到。
- **是否已重装并用安装产物复验**：yes / no + 证据路径。
- **未修项**：登记但未修的，须写明**为什么不修**，不得留空。

**不补事后的 `decision.md`。** 若某轮未按协议开轮，如实补 scope-lock 即可
（scope-lock 能如实回填「做了什么」），但 `decision.md` 的语义是「依据当时证据作出的
验收判断」，**事后写等于伪造判断时点**——见 rounds/0017 的处置先例。
