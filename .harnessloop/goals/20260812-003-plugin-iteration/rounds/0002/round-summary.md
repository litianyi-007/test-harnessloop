## 缺陷与修法

`parseRowCells` 用 `split('|')` 无脑切、`extractRow` 一律按下标取，**全程不校验行的
cell 数是否等于表头列数**。Brief 里出现字面量竖线时该行被多切出 cell、其后所有列
整体右移；竖线后若恰好是已批准的 vendor 名，**Approved-Vendors 守卫也拦不住**
（它拦的是「vendor 名不认识」而非「brief 被截断」）。

**用户裁定走方案 A：强制等宽（BREAKING）。**

理由：允许省略末尾列会让「等宽抵消」永久可用——既有 6-cell 行加一个杂散竖线恰好
变成 7，与格式完全正确的行**长得一模一样，任何基于数格子的规则都分辨不了**。
留一个已知的洞而 CHANGELOG 宣称修好了，正是本项目一直在修的那一族。

## 一并修的两处（第 5 处同族缺陷是评审新发现的）

- **全空占位行处理武断**：`| |` 抛错，而 `| | | | | | | |` 被正常忽略。**同样不承载
  数据，仅因竖线数量不同，一个阻断整个控制面、一个放过。** 现一视同仁。
- **重复 task ID 静默取第一条**（`findEligibleTask` 用 `Array.find`）→ 新增
  `E_DUPLICATE_TASK_ID`，解析期 fail-closed 并指出两处行号。**这是同族第五处。**

## 关于残留边界的如实表述

强制等宽**不等于**「完全消除」。CHANGELOG 按实测精度写：真正的短行现在被拒；同样
意图加一个杂散竖线仍会落在 7 格上静默错位；但**同一个杂散竖线出现在本就写满 7 列
的行里会自曝**（8 vs 7）。**收窄到会自曝的角落，不是数学上归零。**

上一版 CHANGELOG 正是因为夸大（称裸竖线会产生「8 个及以上 cells」）被评审抓住。
