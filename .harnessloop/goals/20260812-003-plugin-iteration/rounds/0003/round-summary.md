# Round Summary — goal 003 / rounds/0003

**修 hopper 缺陷 ⑤（正文只有结构性标记的小节被当成有效 spec），发版 v0.57.0。
评审判 REWORK 一次，而它踩中的正是我自己在 scope-lock 里写死的红线。**

## 结论：达成，但过程比结果更值得记

判据从「marker 之后有无非空白字符」改为**逐行判定**：只要有任意一行不是纯结构性
标记，整节即被接受。方向是「**除了结构性标记之外还有别的**」，不是「不含结构性标记」。

## 评审踩中的红线

scope-lock 明写「**过度拒绝比欠拒绝更糟**」——一个合法 spec 被误判为无内容会让本能
跑的任务 fail-closed 停掉，而缺陷本身只是偶尔送出一份空任务书。

第一版实现恰恰过度拒绝了：`hasSubstantiveContent` **先 `trim` 再判、把缩进信息毁掉**，
于是一个用缩进代码块举例展示 `---` 的合法 spec 被整节判死。

**修法换了原则而不是打补丁**：代码块是作者显式标记的字面内容，判据根本不该往里面看。
围栏行本身算结构，围栏内部与 4 空格/tab 缩进的行一律算内容、连判定都不进。
推论是空围栏块（开闭相邻、内部零行）仍应被拒——实测确实如此。

## 第二条：诊断说谎，属同族

`loadTaskSpec` 有三种不同的 null 成因（没文件 / 没小节 / 小节存在但纯结构），
在调用链里被 `|| ''` 抹平成一种。**小节明明在、只是被拒时，用户看到的是
「No detailed spec section」**——排查会被引到错误方向。

现由可选出参 `diagnostics` 携带 `SPEC_MISS_REASON`，三种原因各说各的话，
成功路径不设。
