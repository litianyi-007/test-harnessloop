## 2. 支配性发现：**5/5 面的硬门开关都握在被守门者手里**

这不是五个独立缺陷，是**同一个结构性属性在五面各现一次**：

| 面 | 零违规的全门旁路 |
|---|---|
| **S5** | 删掉 `goals/<g>/evals.json` → 整个 eval 硬门旁路，**比它所仿的 reference-roots 先例更弱** |
| **S4** | 删除（或从不创建）激活清单 → 零违规单命令总开关；设计自己在备选否决里把同一逻辑判为「万能关门开关」 |
| **S1** | 所有 eval 行写 `system: null` → S1 全部 5 条条件阻塞 kind 永不触发；而声明侧根本没有「哪个 eval 绑定哪个系统」的字段 |
| **S2** | 一份**零证据文件**的账本合法通过 P0–P14 全部检查（`evidence` 允许空数组、`command.evidence` 可为 null）——「证据绑定」整层由被检方 opt-out |
| **S3** | 生产底线做成**黑名单**，被两条路各绕开一次；`retention_max_days` 无上限，M-4 的清理硬门被一个整数完整架空 |

**这与刚把批 2 打停三轮的诊断是同一条**：agent 写记录，也控制记录被核对的每一个输入。
批 2 的结论是收窄机械门职责、把执行力移到异常消费；**批 1 面对的是同一个物理约束，
但用户裁决①要求 evals 是硬门**——两者张力必须正面解决，不能各面自行绕过。

### 2.1 本代码库其实已经有一个答案：`gate_blocking`

`check_setup.py` 的 `GATE_BLOCKING_FILES` 是**「文件缺席本身即阻断」**的既有实现
（三个核心 setup 文件为 `template`/`missing` 时 `gate_blocking: true`，`$harnessloop-continue`
短路到 `needs-setup`）。它恰好堵住 S4/S5 那种「删文件即关门」。

**这意味着我在审核报告附录 C.3.2 的裁决是错的**（见 §4.1）。

## 3. 其余跨面模式

### 3.1 路径身份那一关又被踩（2 面）

- **S1**：symlink 守卫只 `lstat` 叶子文件，**父目录逃逸完全不挡**——把 `.harnessloop/setup`
  做成指向项目外的 symlink，声明文件即从项目外加载、零违规、exit 0。
- **S5**：祖先方向用 `is_under`（canonical 路径上的**字符串前缀**）判定，**大小写不敏感卷上
  可让 eval 静默消失**——正是 v0.25 挨过的那一刀，而草案在否决备选时自己引用过这条理由。

**这是本项目第四、第五次踩同一族**（v0.20 父目录逃逸 / v0.22 symlink / v0.25
大小写不敏感卷）。任何新面涉及路径，必须**默认调用既有的 `_canonical`/`_is_contained`/
`_same_dir`**，而不是重新发明比较。

### 3.2 「文本外观 ≠ 解析结果」（2 面）

S2 与 S4 各自独立发现：**JSON 重复键**与 **bool-as-int** 让「人在 diff 里读到的值」
与「门解析到的值」可以相反。`json.loads` 静默保留最后一个；「未知顶层 key → 整份作废」
是在解析**之后**对已坍缩的 dict 做的，抓不到。

### 3.3 teeth 断言的是实现形状而非规格性质（2 面）

- **S3**：`test-auth-domain-overbroad` 声称了一条**本项目协议已白纸黑字判定为机械不可判**
  的性质，且实测可被一行正则架空；其 teeth 断言的是两个字面 fixture。
- **S1**：teeth #5「versioned 声明在构造上装不下 endpoint」**是假的**——`probe.path` 允许
  `"//evil.example.com/api/status"`，标准 URL 拼接下把主机整个换掉，且 bearer token 会被
  发到那个主机。

### 3.4 追溯判红 vs E1（1 面，但影响面大）

**S4**：回填一条 due 条目会**追溯判红已收盘轮**，唯一出路是改历史产物（撞 v0.12.0 E1）
或删清单。设计声称的「关键性质」只在激活那一刻成立，不是不变量。

### 3.5 一处 fail-open（1 面，但很险）

**S4**：`Feedback` 规范化对未知取值 **fail-open**——一个**全角括号**即可让全部
pass/fail↔positive 一致性硬门整体静默跳过，不产生任何违规。本项目的 decision.md 大量
使用中文全角标点，这不是理论构造。

## 4. 我自己五条裁决被标出问题（附录 C）

五面的 `open_questions` 各自独立标出了附录 C 的硬伤。**逐条处置**：

### 4.1 C.3.2「不做全局 gate_blocking」——**撤回，改判**

裁决原文：外部系统声明「**不做全局 gate_blocking**，改为『active due eval 绑定的系统
未声明/不可用 → 违规』的条件阻塞」。

**证据**：S4 与 S5 两面独立证明，条件阻塞的锚点文件可被删除，形成零违规总开关（§2）。
S1 进一步证明条件阻塞的触发条件（`system` 非 null）本身握在被守门者手里。

**改判**：eval 面的**激活锚点必须具备「缺席即阻断」语义**，采既有 `gate_blocking` 形状。
具体落法（进综合规格）：goal 一旦进入 enforcing，其激活清单缺席 → 违规而非跳过；
清单的存在性与 digest 进 coverage。原裁决"不做 gate_blocking"的顾虑（不让无外部系统的
项目被空配置拖死）仍然成立，因此**范围限定为「已进入 enforcing 的 goal」**，而不是全项目。

### 4.2 C.1-B「新 goal 默认激活」+ C.3.1「最小 teeth = D2」——**需用户裁决**

S3 指出：两条合起来意味着**一个刚 init 的 goal 第一轮就在 enforcing**，而此时
`evals.json` 还是空的、due-set 为空——要么是仪式性绿灯，要么立刻红。

**主会话不自裁**：这直接触及用户裁决①的落地形态（硬门从第几轮开始真的硬）。列入待裁。

### 4.3 C.2「TH-0024 是 TH-0021 硬前置」——S4 提出降级申请，**保持原判**

S4 的设计把激活清单自身作为权威 due-set，因此认为 TH-0024 不再是硬前置。
**但**：S3 独立证明了「due → future 是一条免费、无痕的退休路径」「没有任何字段被约束在
现存轮号附近，因此『声明为 due 但永不到期』是完全合法、永久有效、零违规的配置」。
**权威 due-set 的问题并未因换个载体而消失，只是搬了家。** 保持 TH-0024 为硬前置。

### 4.4 C.1-A 措辞硬伤（S1）与 C.3-4 措辞硬伤（S5）——**接受，措辞修订**

- C.1-A 写「机制骨架（……**每门重判 available**……）可复用」。S1 指出：reference-roots
  重判的是**根**（本地 stat，零权限、确定性）；服务域重判的是**账本**，
  **available 由探针在探针时刻判定，不是门在门时刻判定**。原措辞会把实现者带向
  「让机械门发网络请求」。**修订**：明写「门永不发起网络请求；它核对的是探活账本」。
- C.3-4 写「本项目档位 = standard + 结构化测试资源预授权（既有 push 例外条款的同形扩展）」。
  S5 指出该类比不精确（push 例外是**仓库级不可逆写**的一次性授权，测试资源写是
  **可逆、可清理、按资源域**的持续授权，两者的风险形状不同）。**修订**：删去「同形扩展」
  措辞，改为「与 push 例外并列的第二类预授权，风险形状不同、须各自定义」。

## 5. 对批 1 下一步的判断

**不写综合规格。** 理由：五面各有 3-4 个 blocker，在此之上合成，等于把 18 个 blocker
一次性写进一份规格——批 2 刚用三轮 REWORK 教过这个教训（在有洞的设计上继续叠加，
只会让评审在更大的面上重复同样的判定）。

**应做的是一次系统性修订，而不是五份局部补丁清单**：§2 的支配性发现在五面同时出现，
逐面各修一次会得到五个不一致的局部方案；应当**先定一条统一的「锚点不可删」机制**，
再让五面都挂到它上面。§3.1（路径身份必须复用既有判据）与 §3.2（JSON 解析纪律）同理——
它们是可以一次性写死的**横切约束**，不该在五面各写一遍。

**建议顺序**：
1. 先写一份**横切约束文件**（锚点不可删 / 路径身份复用 / JSON 解析纪律 / teeth 必须
   断言规格性质 / fail-closed 极性），作为五面共同前置；
2. 五面按横切约束各出修订版（可再跑一次 workflow，prompt 里带上横切约束与本轮 blocker）；
3. 然后才合成综合规格；
4. 综合规格再走异构对抗审。
